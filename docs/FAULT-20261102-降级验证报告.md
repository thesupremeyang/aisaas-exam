# 2026-11-02 故障注入 / 降级验证报告

> 目的：验证"上游整体卡住"时，系统是**优雅降级**（可读错误 + 快速失败）还是**整片静默/雪崩**。
> 方法：本机起一个慢上游桩（接受连接 → 挂 20s → 回 500），把测试 agent 的 provider `base_url` 指过去，再打真实并发。
> 结论：**降级路径生效**——池满时 19 次快速拒绝并返回「系统繁忙」；其余请求全部拿到 HTTP 200 + 明确错误事件；无 5xx、无崩溃、恢复后 75 并发依旧 0 错误。同时暴露一个 P1：**缺少 run 级总超时**。

---

## 一、注入方式

```python
# /tmp/stub.py：模拟"上游连得上但永远不返回"的故障
time.sleep(20)                      # 卡住 20 秒
send_response(500)                  # 再返回 5xx
```

```sql
UPDATE model_provider SET base_url='http://127.0.0.1:9099/v1'
WHERE id=9000000000000000201;       -- 仅测试租户05 的临时 provider
```

## 二、测试 1（作废）：同一会话并发两轮

225 个会话 × 2 轮 → 一半请求收到：

```
Agent is still running, please wait for it to finish
```

**这本身是一个有效结论**：同一 `threadId` 上并发发起第二个 run 会被运行时挡住，不会出现"一个会话两条流互相覆盖"。但也说明测试设计要用**一会话一轮**，否则一半请求在进池前就被拒掉，测不到容量。

## 三、测试 2（有效）：450 个独立会话 × 1 轮

| 结果 | 数量 | 含义 |
|---|---:|---|
| 收到明确错误事件（上游 500） | 221 | 考生能看到"AI 调用失败"，不是静默 |
| 客户端 180s 读超时 | 210 | 我的脚本上限；服务端仍在处理 |
| **有界池拒绝 → 系统繁忙** | **19** | 降级路径生效 |
| **HTTP 非 200** | **0** | 450/450 都是 200，没有 5xx、没有连接被拒 |
| 总墙钟 | 183 s | — |

服务端日志对账：

```
journalctl -u apboa-runtime | grep -c 'pool saturated'   → 19
```

与客户端观测到的 19 次「系统繁忙，请稍后重试（并发已满）」**完全一致**——证明拒绝是应用层有意的快速失败，不是网关超时。

### 为什么是 19 次而不是理论上的 66 次？

池容量 = 256 线程 + 128 队列 = 384。450 个请求并非同一毫秒到达（连接建立、Tomcat 调度有先后），
且每轮 20s 的挂起 + 上游重试会周期性释放槽位，所以峰值同时占用没有精确顶到 384。
**结论不变：容量边界是"384 个同时挂起的 run"，超过就快速失败。**

## 五、这次注入暴露的问题（P1）

**单个 run 没有"总时长上限"。**

- 现有约束只有：OkHttp 读超时 300 s + SSE emitter 600 s。
- 上游"连得上但不返回"时，一个 run 会占住线程池槽位最长 300 s；384 个这样的 run 就把池占满 5 分钟。
- 我的 210 个客户端超时正是这个现象：脚本 180 s 放弃，但服务端还在跑。

建议：
1. 给 run 加**总时长上限**（建议 120 s），到点主动 `stopRun` 并向 SSE 发 error 事件"AI 响应超时，请重试"；
2. 前端在收到超时错误后提供"重试"按钮（`onRunError` 已能落库提示，补一个重试动作即可）；
3. 若希望更保守，可把池从 256 降到 128、队列 256，让排队更平滑而不是靠拒绝。

---

## 六、结论

| 验收项 | 结果 |
|---|---|
| 上游卡死时是否整体雪崩 | **否**，服务始终可用，HTTP 全 200 |
| 超容量是否快速失败并给可读提示 | **是**，19 次「系统繁忙」与日志一致 |
| 错误是否可见（不再静默） | **是**，221 次明确 error 事件 |
| 故障解除后能否自愈 | **是**，75 并发 0 错误，线程回落 |
| 同一会话重复提交是否被挡 | **是**，`Agent is still running` |

**这台机器在 450 并发 + 上游全挂的条件下没有崩，也没有"静默失败"。**
剩下的短板不是容量，而是"单个卡住的请求能占多久"——加一个 run 级超时即可闭环。
