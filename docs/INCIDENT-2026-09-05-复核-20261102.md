## 3. 问题一：WebSocket 全量失败 → 这是"爆红"的直接来源

### 现象
【归档】console 日志里 `系统异常: No static resource ws/apboa.` 共 **2,775 次**，其中 **10 点档 2,280 次**（约 38 次/分钟）。夜里也有 24–38 次/小时的基线——说明这是个一直存在、平时没人看见的坑，被 45 个浏览器同时放大成事故。

### 根因（我自己在服务器上验证过）
考试站点挂在 `/web/` 前缀下，前端连的是 `/web/api/ws/apboa`。而 9/5 当天 10:46 之前的 nginx 配置里**只有裸前缀的 ws 规则**：

```
# /etc/nginx/conf.d/apboa.conf.bak-20260905-104646（9/5 10:46:46 改动前的快照）
94:    location /api/ws/  { proxy_pass http://127.0.0.1:3064; }   ← 只有这一个
118:   location /web/api/ { proxy_pass http://127.0.0.1:3060; }   ← 兜底打给 console
```

`/web/api/ws/apboa` 最长前缀匹配落到 `/web/api/` → 转发到 **console:3060**。console 没有 WS 端点，直接抛 `No static resource ws/apboa.`。
websocket 服务（3064）本身是健康的——进程从 9/2 起一直活着，**只是从头到尾没收到过一条考试流量**。

### 为什么"频繁爆红"
前端 `ui/src/websocket/const/websocket.ts` 当时是 `MAX_RECONNECT_ATTEMPTS: 1440`、首重连 800 ms。连不上就无限重连，45 个浏览器各跑一套 → 页面持续弹连接错误红条 + 把 console 日志灌到 53 MB / 374,814 行。

### ⚠️ 对 10/04 文档的一处修正
10/04 文档写"9/9 才补上路由"。**实际是 9/5 10:46:46 就补上了**：

- `apboa.conf.bak-20260905-104646`（改动前的副本，mtime 9/2 23:15）→ **没有** `/web/api/ws/`
- `apboa.conf.bak-20260909-score-all-agents`（9/9 做的副本，`cp -p` 保留了源文件 mtime **9/5 10:46**）→ **有** `/web/api/ws/`，且指向 3064、带 Upgrade 头
- 交叉验证：console ERROR 从 **10 点档 2,492 条 → 11 点档 125 条**。如果 WS 还坏着，11 点不可能掉两个数量级。

所以命名里的 `20260909` 是"什么时候做的备份"，不是"什么时候改的配置"。这条修复在考试中途（10:46）就生效了，**但只救了 WS，救不了对话**——11:10 之后对话又塌了一次。

### 4.3 为什么"没反应也不报错"—— 三个代码缺陷叠在一起

**① 后端把流式异常吞掉了**（`runner-runtime/.../AguiMvcController.java:142-149`）：

```java
result.events()
    .onErrorResume(e -> {
        logger.warn("Agent flux error for thread {}: {} -> {}", ...);   // 只 WARN
        return Flux.empty();                                            // 然后当成正常结束
    })
```

上游报错 / 超时 / 限流 → 只写一条 **WARN**（不进 ERROR 统计）→ 返回空流 → SSE **正常 complete**。前端收到的是"跑完了"，不是"跑失败了"。

**② 前端只在"有文本"时才落库**（`ui/src/composables/chat/useChatStream.ts:76-95`）：
assistant 消息只在 `onTextMessageEnd` 回调里写库。没有文本 → 没有记录。所以 758→199 这个缺口在数据库里"干净"得看不到任何错误痕迹。

**③ 前端根本没处理 RUN_ERROR**（`useChatStream.ts` 的 handlers 里没有 `onRunError`）：
`agent-client.ts:227` 对非 200 响应只构造一个 `RUN_ERROR` 事件，`useChatStream` 没有对应处理函数；`onRaw` 只认 `rawEvent.error` 这一种形状。结果：**HTTP 层失败 = 界面无提示、无气泡、无重试、无日志**。

而用户消息是在**发 run 之前**就存好的（`views/Chat/index.vue` `handleSend`：先 `appendMessage` 再 `sendMessage`）。于是稳定复现这个画面：

> 消息发出去、气泡留在屏幕上、AI 永远不说话、也没有任何红字告诉你为什么。

考生唯一的应对就是再点一次 → 再失败一次 → 雪崩。

### 4.4 触发失败的"上游原因"有哪些（触发项 vs 系统性缺陷）

【归档】runtime 日志当天 458 条 ERROR，可辨认的触发项：

- `HTTP 400` ×32：模型名不在上游白名单（考生配成 `DS-01` / `DeepSeek-flash`，网关只接受 `deepseek-v4-pro` / `deepseek-v4-flash` / `deepseek-v4-flash-vision-exp`）
- `HTTP 401` ×4：API Key 无效
- `max_tokens` 越界 ×2+1：考生填了 800000（上游上限 393216）
- `HTTP 405` ×3、`Agent not found` ×2

**注意区分两件事：**

- **这些 400/401/405 是考生的答题结果**——正确配置模型与算力本来就是实操考题，系统如实透传上游报错是对的，不该"帮忙修好"。
- **真正的系统缺陷是：这些错误没有以任何形式告诉考生、没有落库、没有重试、没有区分"你配错了"和"系统挂了"。** 一个 `DS-01` 的配置错误，在界面上表现为"系统崩溃"，考生无从自查。这是产品缺陷，不是考生问题。

另外，从"同 agent 是否既有成功又有失败"看，失败有两类成因并存：

| 分组 | agent 数 | 失败会话 | 成功会话 |
|---|---|---|---|
| 全失败 | 96 | 166 | 0 |
| **混合** | **24** | 50 | 29 |
| 全成功 | 37 | 0 | 48 |

24 个 agent 出现过"有时能通、有时不通"，说明**除了按 agent 的配置问题，还存在全局的时段性故障**（11:10–11:26 那段最明显）。而 11:10–11:26 段**连 thinking 都没有**，指向的是请求在进入 agent 执行前就被掐掉（HTTP 层拒绝/中断）或运行时整体不可用，而不是模型慢。

> 这一段的确切异常文本已随日志轮转丢失，无法再逐条定位到具体异常类。下次必须靠指标而不是靠翻日志来区分（见 §7）。

## 5. 问题三：交卷被硬拒 → 119 条答卷是"超时强收"的

### 现象【归档】
`系统异常: 请选择平台内智能体后再提交` —— **267 次**（10 点 168 / 11 点 99），另外 `智能体不存在或已禁用` 8 次、`该试题已有提交记录，请勿重复创建` 3 次。

### 根因（已在 2026-10-05 定位并改代码）
`ExamSubmissionServiceImpl.saveDraft()` 原先**无条件**把前端传来的 `agentId` 写回库。前端某次自动保存带了个空 `agentId`，就把已经绑好的值**清成了 NULL**，交卷校验于是硬拒。修法是"`agentId` 为 null 时不覆盖"（与 `workType` 一致）。

### 后果（数据库实证，比文档更狠）

9/5 当天产生的 130 条答卷：

| 指标 | 数值 |
|---|---|
| 超时强制收卷 `TIMEOUT_SUBMITTED` | **119 条（91.5%）** |
| 主动提交 `REVIEW_PENDING` | 11 条 |
| **主动交卷成功的考生** | **仅 4 人**（75 人报名） |
| `form_json` 为空的答卷 | **99 条（76.2%）** |
| 同一考生同一题重复提交 | 7 组 ×2、3 组 ×3 |
| `submitted_at` 最大值 | 12:00:00（到点收卷） |

也就是说：**四分之三的考生那天交上来的是一张白卷，而且不是他们主动交的。**

还有一条：超时收卷的 `submitted_at` 记的是 12:00，但记录 `updated_at` 最晚到 **9/8 21:06**——收卷逻辑跑完得比考试结束晚很久，收卷期间数据没有被冻结。

## 9. 修复清单

### P0（下次开考前必须闭环）

1. **把"静默失败"堵死**（本次复核新增，优先级最高）
   - 后端：`AguiMvcController` 的 `onErrorResume` 不能只 `WARN + Flux.empty()`，必须向前端发一个明确的 `RUN_ERROR` / Raw error 事件，并落一条 `role='error'` 消息。
   - 前端：`useChatStream` 注册 `onRunError`；`agent-client` 非 200 时给可读提示（"模型配置错误：模型名不在白名单"这种，而不是 `HTTP 400`）。
   - 会话页加"该轮失败，点击重试"按钮，并记录 `run_id` 便于对账。
2. **交卷链路兜底**：`saveDraft` 不覆盖空 `agentId`（已改，需确认线上 jar 已包含）；交卷失败必须给出可操作提示。
3. **nginx 固化**：`/web/api/ws/` 与 `/api/ws/` 双写，带 `Upgrade` / `Connection` / 长超时；`nginx -t` + `reload` 纳入发版脚本，不允许手工改生产。
4. **考前 10 分钟五项探活脚本**：账号可登录 → WS 可连通 → 平台内置模型 200 → 智能体可绑定 → 交卷可成功。
5. **考试期间冻结变更**：开考前 2 小时到考试结束，禁止发版/改配置/换前端。

### P1

6. 前端重连收敛（仓库里已改成 40 次 / 10 分钟放弃，**需确认线上产物是这版**）。
7. 超时收卷调度修正：`submitted_at` 与 `updated_at` 相差数小时的问题，收卷必须在结束时刻立即冻结数据。
8. 依赖完整性自检（jgit 这类缺包要在启动阶段就失败）。
