# 智能体考试平台第一性原理能力蓝图

> 基于当前仓库代码、考试相关 SQL、前端页面和既有考试门户 PRD 的规划文档。  
> 日期：2026-09-17  
> 定位：产品能力与系统架构蓝图，不是一次性开发任务清单。

相关的现状审计与开发排期，参见：[智能体考试平台系统分析与开发路线图](./智能体考试平台系统分析与开发路线图.md)。本文件进一步回答一个更基础的问题：**为什么成熟的智能体考试平台必须具备这些能力。**

## 1. 结论先行

当前系统已经具备一条考试 MVP 链路：考试批次、报名、题目、限时提交、AI 初评、评委评分和成绩查询；同时复用了原开源项目的智能体编辑器、模型、知识库、工具、Skill、MCP、运行时和文件服务能力。

但成熟的智能体考试平台，不是把更多页面和 CRUD 功能叠加到原有智能体平台上，而是要建立一套可信的“能力测量系统”。它必须能回答：

> 某个考生在规定时间、规定资源和规定题目下，提交了哪个不可变的智能体版本；这个版本实际完成了哪些测试；系统依据哪些证据得到初评；评委依据哪个评分标准作了什么调整；最终成绩何时由谁发布，之后是否被更正过。

因此，后续建设优先级应当是：

```text
测量目标与规则
  → 受控考试环境
    → 不可变提交物与运行证据
      → 可解释的机器评测与人工复核
        → 版本化成绩、申诉与数据治理
          → 规模化运营与高级监考
```

正式考试前最重要的不是证书、排行榜或炫目的 AI 评分页面，而是先让每一分都能被证明、复核和追溯。

## 2. 从第一性原理重新定义“智能体考试”

### 2.1 考试的本质是测量，不是收集答案

任何考试系统都可以还原为一条证据链：

```text
考试目标
  → 可观察的任务表现
    → 原始证据
      → 评分标准
        → 分数
          → 通过/等级/排名等决策
```

其中任何一环缺失，成绩的可信度都会下降：

| 缺失环节 | 典型后果 |
|---|---|
| 没有明确测量目标 | 评分变成“看起来不错”或“描述写得好” |
| 没有可观察任务 | 无法证明考生真的具备目标能力 |
| 没有原始证据 | 评委只能相信考生自述，无法复核 |
| 没有版本化规则 | 同一份作品可能因题目或 Rubric 被修改而得出不同分数 |
| 没有统一评分流程 | 不同评委、不同时间、不同模型的结果不可比较 |
| 没有结果审计 | 成绩无法解释、纠错或处理申诉 |

对智能体考试而言，考试对象不是一段 Prompt，也不是一份项目说明，而是：

```text
考生 × 任务 × 不可变智能体版本 × 受控资源环境 × 时间窗口 × 评测协议
```

可将实操成绩抽象为：

```text
Score = f(客观测试结果, 运行轨迹证据, 材料证据, 人工判断 | 题目版本、环境版本、Rubric 版本)
```

考生的文字说明可以作为证据之一，但不能替代智能体本身的运行表现。

### 2.2 成熟度的六个判断标准

一个功能是否应该建设，最终都可以回到六个问题：

1. **效度**：测到的是目标能力，还是只测到了表达能力、资源条件或运气？
2. **信度**：同一能力在相近条件下重复测试，结果是否足够稳定？
3. **公平性**：不同考生是否拥有等价的模型、工具、网络、时间和数据条件？
4. **完整性**：题目、作品、证据和成绩是否可能被替换、越权访问或事后篡改？
5. **可解释性**：考生和评委能否理解分数来自哪些证据？
6. **可运营性**：考试高峰、故障、补时、重评和申诉是否有可执行的流程？

这六项比“有没有某个页面”更适合作为平台成熟度的验收标准。

### 2.3 智能体考试特有的难点

传统考试主要保存题面和考生答案；智能体考试还必须处理：

- 模型会变化，输出具有随机性，不能只保存一次聊天结果。
- 智能体由 Prompt、模型参数、Skill、MCP、工具、知识库、记忆和代码等依赖共同组成。
- 一个智能体可能“说明上完成了”，但运行时并没有真正完成任务。
- 工具和外部网络会引入越权、数据泄露、供应链和环境差异。
- 同一智能体可被修改，考后读取实时配置会破坏提交时的事实。
- 评分既有可程序化的客观指标，也有开放式质量判断，不能全部交给规则或 LLM。

所以平台的核心新增能力不是“让考生能创建智能体”，而是“让智能体成为可冻结、可运行、可观测、可比较的考试对象”。

## 3. 当前仓库的能力基线

### 3.1 已经可以复用的基础

原平台已经提供了成熟的智能体开发底座，后续不应重复建设：

- 多租户账号、JWT/SK/ChatKey 鉴权。
- 智能体定义、模型供应商、Prompt、知识库、Skill、MCP、工具、Hook、记忆和多智能体配置。
- AgentScope 运行时、AG-UI、A2A、WebSocket、文件服务和命令代理。
- MySQL、Redis、向量库以及 console/runtime/file/websocket 等分层 runner。

这些能力解决的是“能不能制作和运行智能体”；考试领域还要解决“能不能公平地测量和证明能力”。

### 3.2 当前考试 MVP 的事实边界

当前代码中已经存在 `biz-assessment`，考试控制器集中在 `runner-console/.../assessment`，前端页面集中在 `ui/src/views/exam`，数据库初始化 SQL 位于 `sql/once_db_init`。当前已能看到的领域对象包括：

- `exam_campaign`：考试批次、时间、启用状态和评分配置。
- `exam_enrollment`：考生报名、考试状态和部分成绩字段。
- `exam_question`：题目、场景、要求、成果和排序。
- `exam_submission`：考生作品草稿、选中的智能体、表单和提交状态。
- `assessment_task`：AI 初评异步任务。
- `assessment_report`：初评报告、分项分数、置信度和报告 JSON。
- `assessment_review` / `assessment_result`：人工复核和最终结果。
- `exam_sso_ticket`：考试门户和智能体平台之间的一次性登录票据。

这已经形成“作品提交 + AI 初评 + 人工评分”的业务雏形，但还没有完整形成“考试测量 + 证据链 + 成绩治理”系统。

### 3.3 当前与成熟平台之间的主要断层

| 领域 | 当前形态 | 成熟形态 |
|---|---|---|
| 考试对象 | 以 `form_json` 和 `agent_id` 为主 | 题目版本、环境版本、智能体配置快照和运行轨迹共同构成提交物 |
| 题目 | 批次下直接维护题目 | 题库、题目版本、试卷版本、公开/隐藏测试用例分离 |
| 计时 | 批次时间窗和提交状态 | 考试会话、个人截止时间、补时、断线恢复和多端控制 |
| 环境 | 考生可配置模型，资源边界不充分明确 | 平台统一模型/配额、工具白名单、网络策略和运行时版本固定 |
| 评测 | 主要把表单交给 AI 初评 | 受控运行智能体，先客观断言，再做证据约束下的开放式判断 |
| 评分 | 有人工评分入口，但结果路径需要统一 | 评委分配、Rubric 版本、复核、仲裁、发布和更正形成一条事实链 |
| 权限 | 部分考试管理入口依赖固定账号或通用租户权限 | 考试批次级角色、资源归属、评委分配和最小权限 |
| 数据 | 附件、配置快照、审计事件等关系不完整 | 每个材料、快照、运行和结果都有归属、哈希、版本与审计 |
| 运维 | 有异步 Worker 和轮询页面 | 可抢占任务、重试、超时回收、死信、告警、备份与演练 |

仓库中已有的[系统分析与开发路线图](./智能体考试平台系统分析与开发路线图.md)对权限、交卷、隐私、异步任务和测试门禁做了更细的代码级审计；本文件将这些问题放回“成熟考试必须满足什么”的框架中。

## 4. 必须建设的能力地图

下面按业务闭环而不是按页面来划分模块。优先级含义：

- **P0**：正式考试前必须具备，否则成绩不应作为正式结果使用。
- **P1**：可独立运营一场考试所需。
- **P2**：规模化、质量提升或高级考试能力。

### 4.1 考试定义、规则与版本治理

目标是把“考试到底测什么、什么算完成、如何计分”从散落的 JSON 和页面逻辑中提取出来。

必须支持：

- 考试定义、考试场次和考试状态分离：模板可以复用，场次有独立时间和名册。
- 考试目标、能力维度、通过规则、理论/实操权重和缺考规则。
- 题目版本、评分规则版本、环境策略版本和评测器版本。
- 草稿、审核、发布、锁定、归档等生命周期。
- 开考后禁止修改正在使用的题面、分值、Rubric 和隐藏测试。
- 发布前自动检查：总分、题目、分值、时长、测试用例、附件和评分公式是否完整。

优先级：规则与版本锁定 P0；审批、复制、预览和批次模板 P1；复杂版本分支和实验性试卷 P2。

### 4.2 题库、试卷与题目质量

题库负责沉淀可复用题目，试卷负责定义某一场考试实际使用的题目集合。

每道智能体实操题至少需要：

- 任务场景、任务目标、输入材料、允许资源和禁止行为。
- 公开要求：考生能看到并据此作答。
- 验收点：系统和评委据此判断完成度。
- 评分维度、分值上限、证据要求和扣分规则。
- 公开测试用例和隐藏测试用例。
- 输入、期望行为、断言方式、超时、重试次数和权重。
- 是否允许工具调用、联网、知识库、文件产物或多轮交互。

后续可增加：题库标签、难度、能力维度、版本比较、题目预览、试做、题目统计、A/B 卷和随机抽题。随机组卷应在固定版本和固定规则稳定之后再做。

### 4.3 考生、名册与考试授权

报名不是一行用户资料，而是考生在某一场考试中的资格状态。

需要补齐：

- 考生名册导入、去重、邀请/激活、身份核验和资格审核。
- 批次级业务角色：考生、组织方、评委、监考/考务、系统管理员。
- 评委分配、回收、工作量查看和冲突回避。
- 禁考、取消资格、补考、缓考、特殊时长和单人延期。
- 规则确认、隐私同意、原创/团队声明。
- 考生只能读写自己的报名、考试会话、提交物和结果。
- 评委只能读写被分配且处于授权范围内的作品。
- 组织方只能管理所属组织和批次范围内的数据。

考试角色不能简单等同于原平台的 `TENANT_OWNER/ADMIN/EDITOR/VIEWER`；原平台权限解决的是资源管理，考试角色解决的是考试事务授权。

### 4.4 考试会话、计时与答题过程

`exam_campaign` 的整场时间窗不足以表达一次真实考试。成熟系统需要单独建模 `exam_attempt` 或考试会话：

- 签到时间、实际开始时间、个人截止时间和结束原因。
- 服务端时间为准，客户端倒计时只负责展示。
- 自动保存、版本号、幂等键和“已保存到服务器”的状态。
- 断网重连、刷新恢复、多个标签页/设备控制。
- 单人加时、暂停、强制收卷、误交处理和考务事件。
- 空白交卷、部分完成、正常交卷和超时交卷的区别。
- 会话心跳、设备/浏览器变更和异常事件时间线。

对于智能体考试，答题过程通常不是逐题写选择题答案，而是“在考试工作区内制作—测试—提交智能体”。因此还需要记录关键工作区事件，但不应把所有编辑操作都无目的地永久保存。

### 4.5 标准化的智能体考试环境

这是与普通考试平台最不同、也是最容易影响公平性的模块。

平台必须能为一场考试定义并执行环境策略：

| 环境项 | 必须明确的内容 |
|---|---|
| 模型 | 供应商、模型版本、上下文长度、温度、最大输出、可用时间 |
| 配额 | 请求次数、Token、并发、总费用、单次超时和失败处理 |
| 工具 | 可用工具、参数范围、权限、调用次数和返回数据 |
| MCP | 允许的服务、版本、凭据范围和网络出口 |
| 知识库 | 允许的数据集、版本、检索范围和引用要求 |
| 网络 | 禁止/允许的域名、IP、协议、出站代理和 DNS 策略 |
| 文件 | 可读写目录、大小、类型、执行权限和保留时间 |
| 运行时 | 镜像/依赖版本、沙箱限制、CPU、内存和执行时长 |
| 随机性 | 重复运行次数、可接受波动范围和稳定性评分方式 |

正式考试推荐“平台统一供模 + 固定资源配额 + 白名单工具”。考生自带 API Key 或自定义 Base URL 可以保留给练习模式，但不应默认用于需要横向比较的正式考试。

必须支持提交前和开考前的环境预检：模型可用、工具可用、文件服务可用、评测节点有容量、考生工作区隔离有效。

### 4.6 作品提交、快照与证据管理

正式提交应是一个原子动作：先校验，再冻结，再生成评测任务。

提交物至少包括：

- 考生和考试会话引用。
- 题目版本、试卷版本、Rubric 版本和环境策略版本。
- 选中的智能体 ID，以及提交时的不可变配置快照。
- 模型、Prompt、工具、Skill、MCP、知识库、记忆和依赖的版本/哈希。
- 表单字段的结构化数据。
- 附件清单、类型、大小、哈希、病毒扫描和解析状态。
- 外部链接的登记信息；默认不由服务器主动抓取。
- 提交时间、提交原因、客户端信息和请求幂等键。

快照的原则是：考生交卷后可以继续编辑原工作区，但任何后续修改都不能改变已经提交的考试事实。

### 4.7 智能体自动评测引擎

自动评测应拆成三个层次，而不是直接把表单交给一个大模型：

#### 第一层：可重复的客观测试

- 向冻结的智能体发送标准输入。
- 检查输出结构、内容、引用、工具调用、文件产物、错误处理和超时。
- 对多轮任务记录每一步状态。
- 计算任务成功率、约束违反率、稳定性、耗时、Token 和成本。

#### 第二层：证据约束下的 LLM Judge

- 只评价规则难以程序化表达的开放性指标，如解释质量、方案合理性、可维护性和创新性。
- 输入必须包含题目要求、Rubric、运行轨迹和材料证据，而不是只包含考生自述。
- 使用固定模型、Prompt、输出 Schema 和版本。
- 每个分项都返回分数、理由、证据引用、置信度和风险。
- 模型输出必须经过 Schema、分值上限、总分和证据引用校验。

#### 第三层：人工复核与定分

- AI 初评只能是辅助证据，首期不直接发布正式成绩。
- 低置信度、客观测试与 AI 结论冲突、异常行为或高风险题目必须转人工。
- 评委可以改分，但必须填写理由并保留修改前后的版本。
- 多评委、分差阈值和仲裁作为高风险考试的后续能力。

评测报告应能沿着 `分项 → 证据 → 测试用例/运行 → 提交快照` 反向定位，不能只保存一个不可解释的总分。

### 4.8 评审、成绩与结果治理

成绩不是一个可以覆盖的整数，而是一个有来源、有版本、有状态的业务事实。

必须支持：

- 评委分配和盲评配置。
- 每题、每维度、每个客观指标的评分。
- AI 建议分、评委分、仲裁分和最终发布分的区分。
- 理论成绩导入/接口同步，并记录来源、原始值和校验结果。
- 实操成绩的唯一计算公式、权重、四舍五入、缺考和零分规则。
- 发布前校验：缺评、超范围、分项和总分不一致、证据缺失、未处理异常。
- 批量发布、撤回、重发、重评、成绩更正和版本历史。
- 成绩查询权限、通知、成绩单和后续证书。
- 申诉提交、证据补充、复核、仲裁、结论和通知。

系统应只有一个“发布成绩”的应用服务和一个可识别的结果事实来源，避免不同管理入口各自写入不同表后出现前台和后台结果不一致。

### 4.9 考试诚信、风控与安全

成熟的诚信模块不等于一开始就上摄像头和录屏。应先建设可验证、低侵入的控制：

- 登录、签到、进入考试、保存、切换设备、提交、重试、评分、发布和更正的审计事件。
- 单活跃会话、异常登录、集中复制、频繁切换、临近截止大量改动等风险信号。
- 作品、Prompt、材料和配置的相似度检测；结果只作为风险提示，不自动定罪。
- 团队作品成员、贡献声明和授权记录。
- 题目、隐藏测试和评测数据的隔离。
- 上传文件白名单、大小限制、哈希、病毒扫描、解析隔离和安全预览。
- 把考生提交的文本、附件和智能体输出视为不可信数据，防止 Prompt Injection 影响评测器。
- 限制工具、网络、命令和文件系统的权限；不执行考生上传的未知代码包。
- PII 字段级加密、脱敏展示、日志清理和数据保留期限。
- API Key 使用密钥服务或信封加密，严格限制读取范围和生命周期。

只有当业务明确需要并完成隐私、合规、客户端兼容和证据政策设计后，才考虑摄像头、录屏、锁屏浏览器等重监考。

### 4.10 通知、考务支持与运营

考试不是单个用户流程，而是一个需要组织方持续操作的事件系统。

需要提供：

- 考前须知、规则确认、开始提醒、临期提醒、交卷确认、评测失败和成绩发布通知。
- 考生名册、签到、在线、已进入、已保存、已提交、评测和发布漏斗。
- 考务事件中心：断网、服务故障、补时、暂停、强制收卷、重试和人工处置。
- 评测队列深度、成功率、P95 耗时、模型错误、节点健康、Token、成本和告警。
- 备份恢复、数据导出、数据删除和分角色下载。
- 练习模式与正式考试模式的明确隔离。

### 4.11 质量分析与持续改题

当考试至少运行过几轮后，平台应反过来分析考试本身：

- 题目难度、空答率、完成时长和区分度。
- 客观测试与人工评分的一致性。
- AI 与人工评分的偏差、不同分段的误差和低置信度比例。
- 不同模型、运行时和题目版本对成绩的影响。
- 争议率、申诉率、重评率和题目异常率。
- 题目是否考到了目标能力，是否被某个偶然细节主导。

这些数据用于校准题目和评分标准，不应简单转化为排行榜。

## 5. 目标领域模型与模块边界

### 5.1 建议的领域分层

当前系统将部分信息放在 `exam_campaign.config_json` 和 `exam_submission.form_json` 中，适合早期原型，但不适合承载长期稳定的考试事实。建议逐步形成以下边界：

| 领域 | 关键对象 | 主要职责 |
|---|---|---|
| 考试定义 | `exam_definition`、`exam_session` | 定义考试产品与某次具体开考 |
| 题库试卷 | `question_bank_item`、`question_version`、`paper_version` | 题面、分值、Rubric、测试用例与发布锁定 |
| 考务资格 | `exam_role_assignment`、`exam_enrollment` | 名册、角色、资格、补时和分组 |
| 考试会话 | `exam_attempt`、`exam_event` | 签到、计时、保存、设备和考务事件 |
| 作品证据 | `exam_submission`、`submission_material`、`agent_snapshot` | 结构化答卷、附件和智能体冻结快照 |
| 评测执行 | `assessment_task`、`assessment_run`、`assessment_trace` | 排队、运行、断言、轨迹和成本 |
| 评分复核 | `assessment_report`、`review_assignment`、`assessment_review` | AI 建议、评委评分、仲裁和理由 |
| 结果治理 | `assessment_result`、`appeal_case`、`certificate` | 发布、撤回、更正、申诉和证书 |
| 平台治理 | `audit_event`、`notification`、`retention_policy` | 审计、通知、保留、导出和删除 |

不要求一次性创建所有表，但每次新增字段都应先判断它属于哪个事实域，避免继续把可审计事实堆到任意 JSON 中。

### 5.2 从当前对象到目标对象的演进

| 当前对象 | 建议演进 | 原因 |
|---|---|---|
| `exam_campaign` | 拆成考试定义与考试场次，或明确其承担哪一层 | 模板和具体开考的生命周期不同 |
| `exam_question` | 引入题目版本和试卷版本 | 开考后题面、分值和规则必须冻结 |
| `exam_enrollment` | 保留报名，新增批次角色与 `exam_attempt` | 报名资格不等于一次考试会话 |
| `exam_submission` | 关联题目版本、会话、环境和快照 | 交卷必须能重建当时事实 |
| `form_json` | 逐步迁移为结构化答卷 + 材料关系 | 附件、PII 和版本信息不应混在一处 |
| `assessment_task` | 增加运行、重试、超时和死信信息 | 任务状态需要支持可靠运营 |
| `assessment_report` | 保存证据引用、测试结果和评测器版本 | 报告必须可解释、可重放 |
| `assessment_review/result` | 统一复核服务，结果版本化 | 只能有一个最终发布事实来源 |

### 5.3 关键不变量

这些不变量比具体表名更重要：

- 考生不能读取或写入他人的考试资源，即使双方属于同一租户。
- 评委不能访问未分配的作品，组织方的跨范围访问必须有独立权限和审计。
- 开考后，参与当前考试的题面、Rubric、隐藏测试和环境策略不可变。
- 一份正式提交只能指向一个明确的题目版本、会话和智能体快照。
- 同一提交不能存在多个活动评测任务。
- 同一结果版本不能被静默覆盖；更正必须产生新版本并记录原因。
- 每个分项分数都必须能引用至少一种有效证据，或明确标记为人工判断。
- 原始材料、敏感字段、密钥和运行轨迹的访问必须分别授权、分别审计。
- 后台任务必须显式恢复租户和业务上下文，不能把“忽略租户过滤”当作业务授权。

## 6. 可信评测的目标流程

```mermaid
flowchart LR
  A[定义考试目标] --> B[发布题目/试卷/Rubric版本]
  B --> C[配置标准考试环境]
  C --> D[考生创建并测试智能体]
  D --> E[服务端校验正式提交]
  E --> F[冻结题目、环境、智能体和材料快照]
  F --> G[创建可重试评测任务]
  G --> H[受控 Runtime 执行公开/隐藏测试]
  H --> I[规则断言与运行指标]
  I --> J[证据约束下的 LLM Judge]
  J --> K[评测报告与置信度]
  K --> L[评委复核/仲裁]
  L --> M[发布版本化成绩]
  M --> N[通知、申诉、统计与改题]
```

其中需要特别坚持三条边界：

1. **提交边界**：提交时冻结事实，不能考后读取实时智能体配置替代快照。
2. **评测边界**：评测器可以读取受控证据，但不能被考生材料中的指令操纵，也不应主动访问未知外部链接。
3. **成绩边界**：AI 可以给建议和风险，最终发布由统一的评分服务完成，并留下版本和审计。

## 7. 建议的评分体系

### 7.1 三类分数组成

| 分数来源 | 适合评价的内容 | 约束 |
|---|---|---|
| 规则分 | 成功/失败、结构、格式、引用、工具调用、耗时、产物 | 结果可重复，规则需版本化 |
| AI 建议分 | 解释质量、方案合理性、开放式质量、创新性 | 必须引用证据，输出 Schema 固定，低置信度转人工 |
| 人工最终分 | 综合判断、边界案例、异常解释和仲裁 | 受 Rubric 上限约束，修改需要理由和审计 |

不要让一个“AI 总分”同时承担客观测试、开放式判断和最终裁决三种职责。

### 7.2 每个评分维度的最小记录

每个维度至少记录：

- 维度编码、名称、最大分和 Rubric 版本。
- 客观测试得分、AI 建议分、人工最终分。
- 证据引用：测试用例、运行轨迹、附件或表单字段。
- 评分理由和风险说明。
- 置信度、评测器模型、Prompt 版本和运行时间。
- 修改前后分数、修改人、修改时间和修改原因。

### 7.3 稳定性与随机性

大模型输出无法保证完全确定，因此不应假设一次运行就代表能力。对于需要严肃比较的题目，应配置：

- 同一测试的重复运行次数。
- 可接受的输出差异和判定容差。
- 超时、限流、模型错误和工具错误的处理方式。
- 偶然成功、偶然失败和结果方差的记录。
- 是否允许因平台故障重跑，以及重跑是否替换原始证据。

重跑应产生新的 `assessment_run`，而不是覆盖原运行记录。

## 8. 与当前代码架构的落地关系

建议保留原平台的职责，把考试能力作为独立领域逐步增强：

```text
common
  └─ 考试实体、DTO、VO、枚举、脱敏模型和跨模块契约

biz/biz-assessment
  └─ 考试领域服务、状态机、授权、提交、评分、结果和任务编排

runner-console
  └─ 组织方、考务、评委和系统管理 API

runner-runtime
  └─ 受控智能体运行、测试用例执行和轨迹采集

runner-file
  └─ 附件上传、扫描、解析、预览和保留策略

runner-websocket
  └─ 任务状态、考务事件和通知推送

assessment-worker（早期可暂留在 console，规模化后独立）
  └─ 可靠领取任务、调用 runtime、重试、死信和报告落库

ui/src/views/exam
  └─ 考生、评委、组织方和结果页面；业务判断以服务端为准
```

几个边界必须明确：

- 考试门户通过 SSO 和受控桥接接口访问智能体平台，不直连既有平台数据库。
- console 负责考试事务，不直接执行考生代码、工具或未知附件。
- runtime 负责运行冻结的智能体和测试用例，不能自行决定最终成绩。
- WebSocket/SSE 只负责通知，任务和成绩事实仍以数据库/可靠队列为准。
- 数据库迁移应从零散的 `once_db_init` SQL 逐步演进为可重复、可校验、可回滚的迁移流程。

## 9. 分阶段建设路线

### 阶段 0：定义“考什么”和“什么证据算数”

交付：

- 正式考试与练习模式边界。
- 个人作品还是团队作品。
- 理论考试自建、外接还是只导入成绩。
- 是否统一供模、是否允许 BYOK、网络和工具政策。
- 每类题目的能力目标、验收点、Rubric、客观测试和人工判断边界。
- 评分公式、及格规则、缺考/超时/故障/申诉政策。

退出条件：任何关键成绩字段都能回答“它在测量什么、证据在哪里、谁可以修改”。

### 阶段 1：建立可信交卷底座（P0）

优先实现：

- 独立考试角色、批次授权、评委分配和资源归属校验。
- 服务端 DTO、字段/题目/附件/时间窗校验、乐观锁和幂等。
- `exam_attempt`、单活跃会话、服务端计时、断线恢复和超时分类。
- 题目/Rubric/环境/智能体/附件快照。
- PII、API Key、自定义 URL、文件上传和 Prompt Injection 的安全边界。
- 唯一的复核/发布服务和版本化结果。
- 审计事件、备份策略、基础告警和权限测试。

退出条件：在不依赖前端限制、不直接改库的情况下，能够证明“谁在何时提交了什么”。

### 阶段 2：形成可运营的考试产品（P1）

优先实现：

- 名册导入、激活、分组、公告、规则确认和考务状态。
- 题库/试卷/版本/发布/预览/模拟作答。
- 每人特殊时长、补考、缓考、强制收卷和故障处置。
- 标准模型、工具和网络策略，以及开考前资源预检。
- 材料扫描、解析、预览、下载授权和保留策略。
- 评委工作台、批量分配、AI 报告、评分草稿和发布前校验。
- 站内通知、考务事件中心和运营看板。

退出条件：组织方可以仅使用管理界面完整组织一场考试，不需要手工插 SQL 或修改配置文件。

### 阶段 3：实现可信的智能体评测（P0/P1 核心）

优先实现：

- 公开/隐藏测试用例和测试数据版本。
- 受控 Runtime 执行冻结智能体。
- 轨迹、工具调用、检索引用、文件产物、Token、耗时和错误采集。
- 规则断言、重复运行、稳定性和安全测试。
- 证据约束下的 LLM Judge、结构化输出校验和置信度路由。
- AI 与人工评分抽样校准。

退出条件：至少一类关键题型不再依赖考生自述，评委能从报告跳转到测试结果和原始证据。

### 阶段 4：规模化与高级治理（P2）

按业务需要增加：

- 多评委、双盲、分差阈值和仲裁。
- 申诉工单、复核证据包和完整沟通记录。
- 证书、成绩单、组织级统计和能力画像。
- 题目难度/区分度分析、评分器校准和版本对比。
- A/B 卷、随机组卷、题目曝光控制和高级题库治理。
- 轻监考增强，必要时再评估摄像头/录屏/锁屏浏览器。
- 多节点评测、队列分区、成本预算、自动扩缩容和灾备演练。

## 10. 正式考试上线门槛

至少满足以下条件，才建议把成绩用于正式认证、晋级或排名：

- 能证明考生、考试会话、题目版本、环境版本和智能体快照之间的关系。
- 后端完成所有权、角色、租户、时间窗、版本、附件和状态校验。
- 开考后题目、Rubric、隐藏测试和环境策略不会被静默改变。
- 评测任务不会重复执行、永久卡住或失败后无处处理。
- 评测结果有客观测试、运行证据、AI 建议和人工复核的清晰区分。
- 成绩发布只有一个事实来源，撤回/更正会形成新版本并记录原因。
- PII、密钥、附件和运行轨迹不会以越权或明文形式泄露。
- 完成考生、评委、组织方三角色的端到端模拟考试。
- 完成集中自动保存、集中交卷、模型不可用、runtime 重启、文件服务异常和 Redis/数据库故障演练。
- 完成水平越权、垂直越权、SSRF、恶意上传、提示注入和日志泄露测试。
- 有明确的人工兜底、考务 Runbook、联系人、数据备份和恢复步骤。
- AI 与人工分数的一致性达到业务设定阈值；未达到时，AI 只能作为建议，不得自动发布。

## 11. 资源有限时的最小可信版本

如果当前团队无法一次性建设完整通用考试平台，建议把范围收敛为：

> 固定试卷、固定时间、统一模型、受控工具、单人智能体作品、3～5 个隐藏测试用例、规则分 + AI 辅助解释 + 单评委最终发布。

这个最小版本可以暂不做：

- 完整理论题库和复杂在线答题引擎。
- 自适应考试和复杂随机组卷。
- 全量双盲多评委。
- 证书商城、排行榜和社交分享。
- 摄像头、录屏和锁屏浏览器。

但不能暂不做：

- 题目和 Rubric 版本冻结。
- 智能体和依赖配置快照。
- 受控运行和最小测试证据。
- 后端授权、提交校验和审计。
- 统一结果发布与更正。
- 任务可靠性、隐私保护和故障兜底。

## 12. 需要业务负责人明确的决策

技术可以提供实现方案，但以下问题会直接改变系统边界，不能由代码默认：

1. 这是个人能力考试、团队作品考试，还是两者都支持？
2. 正式考试是否允许考生自带模型、Key、知识库和外部服务？
3. 智能体可以使用哪些工具、MCP、网络和文件资源？
4. 考生交卷后是否允许继续修改原工作区？修改后的版本是否用于复赛或练习？
5. 理论成绩来自哪里，理论与实操如何合成，及格是总分还是分项均及格？
6. AI 初评的业务定位是提示、分数建议，还是可在低风险题型中自动评分？
7. 什么情况必须二评、仲裁、重跑或允许申诉？
8. 是否需要身份证号等敏感身份信息，能否用学号/培训编号替代？
9. 数据、附件、运行轨迹、Prompt 和密钥分别保存多久？
10. 正式考试需要何种监考强度，相关隐私与合规责任由谁承担？

## 13. 最终判断标准

可以把平台是否“成熟”压缩成一个验收问题：

> 任取一名考生、一份提交物和一个最终分数，平台能否在不依赖个人记忆、不依赖手工改库的情况下，重建当时的题目、环境、智能体、运行、证据、评分、发布和更正全过程？

如果答案是否定的，系统仍然是“有考试功能的智能体平台”；如果答案是肯定的，才开始接近“可以对智能体能力负责的考试平台”。

下一步最合理的动作不是继续添加外围页面，而是围绕阶段 0 和阶段 1 建立一条最小可信链路，再用一类真实题型验证阶段 3 的评测闭环。
