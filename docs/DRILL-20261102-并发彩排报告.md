## 五、彩排挖出的新问题：每个请求 new 一个 OkHttp client（已修复）

### 现象

225 并发那一档跑完 10 分钟后，runtime 线程数仍是 **310**，其中：

```
229  OkHttp api.deepseek.com
 11  quartzScheduler
 10  http-nio-3061-e
```

这些线程全部处于 `S`（睡眠）状态，**不回收**。

### 根因

`engine/.../model/HttpTransportHelper.createOkHttpTransport()` 每次调用都 `new` 一个 `OkHttpTransport`；
而 agent 工厂是「每个请求构建一次模型」（`() -> iAgentFactory.getAgent(id, tenantId)`），
于是**每次对话都会连带创建一套 OkHttp dispatcher 线程池**，client 从不 shutdown。

影响：一场 300 人 × 多轮的考试，会留下成百上千个常驻线程（每线程约 1 MB 栈），
最终表现是 `unable to create native thread` 或整机上下文切换飙升——**典型的"越考越慢、第二场直接崩"**。

### 修复

按「超时组合」缓存 transport（OkHttpClient 本身线程安全、设计上就该复用）：

```java
private static final Map<String, HttpTransport> TRANSPORT_CACHE = new ConcurrentHashMap<>();
TRANSPORT_CACHE.computeIfAbsent("okhttp:" + connectTimeout + ":" + readTimeout, k -> OkHttpTransport.builder()...build());
```

### 修复前后对比（同样 75 并发）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 跑完即刻 OkHttp 线程 | —— | 25 |
| 50 秒后 OkHttp 线程 | **229（10 分钟不降）** | **3** |
| 50 秒后总线程 | 310（不降） | 188 → 121 → **83（回到基线）** |

## 六、结论与建议

1. **平台容量：225 并发（3× 真实规模）零错误。** 按当前 4C/15G 单机，75 人考试有充足余量。
2. **延迟瓶颈在上游模型**，不在平台。若要压 300+，先按租户拆分 key / 提高上游配额。
3. **线程泄漏已修**，这是本轮最有价值的产出；建议后续每轮发版都跑一次"75 并发 + 跑完看线程数回落"。
4. 仍建议赛前做一次**故障注入**：把某个 agent 的 base_url 指向黑洞地址，验证有界池的"系统繁忙"降级，以及上游整体卡死时的表现。
5. 本轮未覆盖：交卷/收卷尖峰（需要完整场次数据）、WS 真实业务消息、多节点。下次彩排建议用真实场次 + 75 个真实账号跑一遍完整流程。
