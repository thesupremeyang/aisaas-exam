## 2. 主因一：Nginx 缺 `/web/api/ws/` 路由，WebSocket 全量失败

### 2.1 现象

```
ERROR c.h.a.c.e.GlobalExceptionHandler - 系统异常: No static resource ws/apboa.
```

共 **2,775 次**，按小时分布：

```
00  32    01  38    02  27    03  27    04  24    05  27
06  30    07  24    08  64    09 202    10 2280
```

注意两点：

- **夜里也有 24–38 次/小时的基线**：说明有一个长期打开的页面/探针在不停重连，这是一个一直存在、
  平时没人注意的缺陷；
- **10 点暴涨到 2,280 次（约 38 次/分钟）**：45 位考生同时进入考试，缺陷被放大成事故。

### 2.2 根因（有配置原文为证）

考试站点挂在 **`/web/` 前缀**下，但 9/5 10:46:46 的 Nginx 配置备份
`/etc/nginx/conf.d/apboa.conf.bak-20260905-104646` 里只有裸前缀的 ws 规则：

```
 84:    location = / {
 88:    location /web/ {
 94:    location /api/ws/ {                 ← 只有 /api/ws/，没有 /web/api/ws/
 96:        proxy_pass http://127.0.0.1:3064;
105:    location /web/api/runtime/ {
106:        proxy_pass http://127.0.0.1:3061/runtime/;
118:    location /web/api/ {
119:        proxy_pass http://127.0.0.1:3060/;    ← 兜底：打给 console
```

前端请求的是 `/web/api/ws/apboa`。Nginx 前缀匹配取最长者，命中 `location /web/api/`，
被转发到 **console:3060**。console 根本没有 WS 端点，于是抛 `No static resource ws/apboa.`，
**永远连不上**。

### 2.3 为什么会"频繁爆红"

前端 `ui/src/websocket/const/websocket.ts`：

```ts
MAX_RECONNECT_ATTEMPTS: 1440,   // 最多重连 1440 次
INITIAL_RECONNECT_DELAY: 800,   // 首次 800ms
MAX_RECONNECT_DELAY: 30000,
PING_INTERVAL: 20000,
PONG_TIMEOUT: 8000,
```

连不上 → 800ms 后重连 → 再失败 → 退避 → 再重连，最多 1440 次。
45 个浏览器各跑一套重连循环，于是：

- 页面上持续弹出连接错误/红条（用户感知的"频繁爆红"）；
- 每次失败 console 打一条 ERROR + 一坨 WARN 上下文，**把日志灌到 53 MB**。

### 2.4 WebSocket 服务本身是健康的

```
32868  Wed Sep  2 23:15:36  /usr/bin/java -Xms256m -Xmx512m -jar runner-websocket-1.0-SNAPSHOT.jar
LISTEN 0 100 *:3064  users:(("java",pid=32868,fd=9))
```

该进程 9/2 启动、9/5 当天一直在跑、至今（10/4）仍在运行，监听 3064 正常。
**它不是崩了，是从头到尾一节课都没收到考试流量。**

### 2.5 修复时间线：故障后 4 天才补上

```
最早出现 location /web/api/ws 的备份：
  /etc/nginx/conf.d/apboa.conf.bak-20260909-score-all-agents   ← 2026-09-09
```

即 **9/5 考完 → 9/9 才补上路由**，中间 4 天这个坑一直开着。后续还有
`apboa.conf.bak-ws-align-20260928-105426`（9/28 又一次 ws 对齐）。

### 2.6 第二层坑：前端硬编码 `ws://`，HTTPS 下会被浏览器拦截

9/5 的 Nginx 配置里已经有人写了注释（第 134–136 行）：

```
# 注意：前端 websocket 客户端当前硬编码 ws://（见 ui/src/websocket/const/websocket.ts），
#       HTTPS 页面下浏览器会以混合内容（mixed content）拦截，
#       要么把该文件改为 wss:// 后重新构建前端。
```

也就是说，**就算 Nginx 路由补对了，只要页面是 HTTPS、前端还是硬编码 `ws://`，浏览器仍会拒绝连接**。
仓库里的 `websocket.ts` 现在已经改成动态协议（`isHttps ? 'wss:' : 'ws:'`），
但**线上前端产物是否是修复后重新构建的，需要单独确认**（见第 8 节待办）。

## 3. 大模型调用失败 32 次——**不是系统缺陷，是考试内容**

> **重要归因修正（2026-10-05）**：正确配置大模型与算力本身就是实操考试的一部分。
> 考生把模型名配成 `DS-01` / `DeepSeek-flash`、把 provider 指向不可达的地址，
> 属于**答题错误**，系统如实返回上游的 400/401 是正确行为，**不应计入系统故障**。
> 同理，库中残留的"野模型"配置与指向 `api.openai.com` 的 provider 也是考生/租户的自主配置，
> 平台不应主动清理。以下仅作为现场现象记录，不作缺陷处理。

runtime 日志，全部集中在 **10 点**：

```
32×  HTTP error: status=400  The supported API model names are
     deepseek-v4-pro, deepseek-v4-flash, and deepseek-v4-flash-vision-exp,
     but you passed "DS-01" / "DeepSeek-flash".
 4×  HTTP error: status=401  Authentication Fails, Your api key ...
 2×  HTTP error: status=400  Invalid max_tokens value
 2×  Agent not found: exam-candidate-83a392ca9df11c4b-001
 3×  HTTP error: status=405
```

**现象**：考生侧配置的模型名（`DS-01`、`DeepSeek-flash`）不在上游网关白名单里
（只接受 `deepseek-v4-pro` / `deepseek-v4-flash` / `deepseek-v4-flash-vision-exp`），
另有 4 次 API Key 鉴权失败、2 次 `max_tokens` 超上限。

**定性**：以上均为**考生答题结果**，非系统缺陷。实操考试本就考察"能否正确接入大模型与算力"，
考生配错即应报错，系统如实透传上游响应是正确的。

**唯一需要系统侧关注的**：`Agent not found: exam-candidate-...` 2 次——考生专属智能体没建出来
或已被清理，这属于平台初始化逻辑，需确认是系统问题还是考生自己删了。

## 4. 交卷失败 267 次——**归因待定，很可能也不是系统缺陷**

```
系统异常: 请选择平台内智能体后再提交
  10 点 168 次
  11 点  99 次
```

含义：提交接口要求考生已绑定一个"平台内智能体"，但提交时没拿到 / 拿到的智能体不合法。

关联证据：

- `智能体不存在或已禁用` 8 次
- `Agent not found: exam-candidate-...` 2 次
- `该试题已有提交记录，请勿重复创建` 3 次（考生反复点提交的重试痕迹）

**推断的完整因果链（待验证）**：

```
考生登录 → 进入考试 → 创建/绑定专属智能体
                            ↓ 可能原因 A：考生没做对这一步（考试内容）
                            ↓ 可能原因 B：WS 连不上导致状态没同步（系统问题，已修）
                     智能体未正确绑定 / agentId 未落库
                            ↓
              交卷时校验失败："请选择平台内智能体后再提交"
                            ↓
              考生反复点击 → 267 次失败 + 3 次"请勿重复创建"
```

> **归因修正（2026-10-05）**：既然"搭建并绑定智能体"也是实操考试的内容，
> 这 267 次里相当一部分很可能是考生没完成该步骤的**答题结果**，不能一律算系统故障。
> 但其中受 WS 故障牵连的部分（原因 B）确属系统问题，二者比例目前无法从日志中区分。
> 建议下次考试前用一次小规模实测来区分：若所有人都能正常绑定，则此项可整体移出缺陷清单。

11 点还有 99 次，说明**直到考试末尾这个链路都没恢复**。

## 8. 修复 / 加固清单

### P0 — 下次开考前必须完成

1. **固化 Nginx WS 路由**：`/web/api/ws/` 与 `/api/ws/` 都要有，并带上
   `Upgrade` / `Connection: upgrade` / `proxy_read_timeout`。
   建议把 `location /web/api/ws/` 写成显式规则，不要依赖 `/web/api/` 兜底。
2. **确认线上前端产物含动态协议修复**：当前仓库 `websocket.ts` 已是
   `isHttps ? 'wss:' : 'ws:'`，需确认线上 `/web/` 下的 bundle 是这个版本（对比构建时间）。
   若不是，重新构建部署——否则 HTTPS 下 `ws://` 会被浏览器当混合内容拦截。
3. **只校验平台内置模型**：考前对**平台自带**的模型与 API Key 做一次探活，断言 200。
   ⚠️ 不要校验考生自己配置的模型——配错是考试内容，系统不应代劳。
4. **交卷失败的提示要可操作**：`agentId` 未绑定时，把"请选择平台内智能体后再提交"
   换成明确指出缺哪一步的提示，并给"重新初始化我的考试智能体"入口，
   让考生能分清「我还没做这一步」和「系统出问题了」。

### P1 — 稳定性

5. **前端重连策略收敛**：1440 次重连 × 45 人 = 日志灾难。改为
   「最多 N 次快速重试 → 退避到 30s → 超过阈值后停止并提示用户刷新页面」，
   并在服务端对同一会话的 WS 失败做**聚合限流日志**（例如同 session 1 分钟内只打 1 条 ERROR）。
6. **上线前依赖完整性检查**：jgit 这类缺失要能在构建/启动阶段被发现（启动自检或依赖清单比对）。
7. **修掉路径拼接 bug**：`/wwwroot/C:\Users\Administrat...` 说明有地方把客户端传入的相对路径
   直接拼到了 Linux 基目录上，既报错又有路径穿越风险。

### P2 — 可观测性

8. **加容量与健康的黄金指标告警**：ERROR 数/分钟、WS 连接成功率、模型调用成功率、
   Tomcat 活跃线程、Druid 活跃连接。9/5 这种量级如果提前 10 分钟就能看到。
9. **考试当天开"静默模式"**：把 `AuthInterceptor [DEBUG3]` 这类上下文 WARN 降到 DEBUG，
   避免真正的问题被 22 万条噪音淹没。
10. **考前 checklist 脚本化**：账号可登录、WS 可连通、模型可调用、智能体可绑定、
    交卷可成功——五项一键跑通再开考。
