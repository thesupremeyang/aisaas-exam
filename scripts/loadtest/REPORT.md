# 实操考试系统并发压测报告

> 方法沿用理论（简答）考试系统的 `LOADTEST-METHOD.md`（`~/Desktop/考试系统/LOADTEST-METHOD.md`）。
> 工具链改为 Node 脚本 + 输出 JMeter 同格式 `.jtl`（本机没装 JMeter）。
> 本报告只记录**本轮结果**；方法论本身见那份手册，**本系统的差异与本轮新踩的坑见 §八**。

测试时间：2026-10-04　被测：`exam-local` profile（console 3160 / apboa_exam 库）

---

## 一、结论先行

| 结论 | 数字 |
| --- | --- |
| **没有找到错误拐点** | 100 → 2500 并发，**全档 0% 错误率**，12501 个样本无一失败 |
| **真正的约束是延迟，不是可用性** | enter p95 从 195ms（100 并发）涨到 3799ms（2500 并发），线性增长 |
| **建议容量** | **≤ 800 并发**（约 2400 考生）体验良好，p95 约 1 秒；<br>1500 并发 p95 已到 2.1 秒，考生会明显感到卡顿 |
| **瓶颈方向** | 数据库连接池（Druid 默认 8）+ Tomcat 线程（默认 200），但**本轮 A/B 未能验证**（见 §五，被造数污染污染了） |

一句话：**这套系统不会把你考崩，但会把考生卡住。** 削峰比扩容更划算。

## 二、测了什么

对应方法论 §2 的 S1/S2/S3，映射到本系统的三个真实接口：

| 编号 | 场景 | 接口 |
| --- | --- | --- |
| **S1** | 开考瞬间 | `POST /exam/candidate/submissions/enrollments/{id}/submissions` |
| **S2** | 答题中自动保存 | `PUT /exam/candidate/submissions/{id}/draft` |
| **S3** | 交卷瞬间 | `POST /exam/candidate/submissions/{id}/submit` |

每个虚拟考生的完整链路：登录 → **集合点** → S1 → 两次 S2（间隔 600ms）→ **集合点** → S3。

未覆盖：S4 到点自动交卷（服务端定时任务）、S5 查分。

## 三、被测环境（数字的解释前提）

方法论 §3.2 要求先写清环境，否则数字无法解释。

| 项 | 本次 | 生产 | 对结果的影响 |
| --- | --- | --- | --- |
| 机器 | Apple M1 / 8 核 / 8GB | 服务器 | CPU 与内存都是瓶颈上限，生产会明显更好 |
| 应用实例 | console **单实例** | 可多实例 | accept 与线程池能力未翻倍 |
| Tomcat 线程 | **默认 200**（未配置） | 可调 | 超过 200 并发的请求在 Tomcat 排队 |
| DB 连接池 | **Druid 默认 8**（exam-local 未配置 druid） | 可调 | 8 条连接是所有 DB 操作的串行瓶颈 |
| 数据库 | MySQL 8.0.46 本地 | 托管 MySQL | 本地库还跑着压测客户端，资源争抢 |
| 接入层 | 裸 Spring Boot | Nginx | 无连接复用、无 accept 队列调优 |

**结论：本报告的数字是「能力下限」，不是上限。** 生产同样并发下拐点会明显右移。

## 四、结果

### 4.1 分档扫描（每档前清理造数，库大小一致）

| 并发 | enter p50 | **enter p95** | submit p50 | **submit p95** | draft p95 | 错误率 | 集合点窗口 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 153 | **195** | 106 | **172** | 32 | 0% | 0.06s |
| 400 | 389 | **567** | 359 | **572** | 20 | 0% | 0.14s |
| 800 | 570 | **1056** | 619 | **1189** | 486 | 0% | 0.25s |
| 1500 | 1089 | **2071** | 1143 | **2090** | 1510 | 0% | 0.32s |
| 2500 | 1983 | **3799** | 2016 | **3740** | 3201 | 0% | 0.54s |

（单位 ms。分位数按 §5.1 只对**成功样本**计算；本轮全成功，所以与全样本口径一致。）

### 4.2 集合点确实生效

发起窗口就是「这批请求的第一个和最后一个之间隔了多久」：

- 100 并发 → 0.06s，2500 并发 → **0.54s**

2500 个「进入考试」请求在半秒内全部发出，是真实的「同一瞬间点击」，不是被 rampup 摊平。**这是数字可信的前提。**

### 4.3 错误归因（§7 三段法）

- **第一段（错误类型）**：无错误可归因。没有 `Connection refused`，没有 500。
- **第二段（时间分布）**：无错误。
- **第三段（端点分布）**：所有端点 0% 错误 → **应用逻辑本身是健康的**，不存在 bug 型失败。

这与理论考试系统形成鲜明对比：那套系统在 280 并发就出现 `Connection refused`（连接队列打满），
本系统到 2500 并发仍能全部受理。差异来自运行时——Java/Tomcat 的线程池模型比裸 Node 更能扛连接风暴。

### 4.4 延迟形态：排队，不是尖峰

延迟随并发**线性**增长（100→2500，p95 涨 19 倍），且 draft 在 400 并发时反而最快（p95 20ms）。
这说明系统是**被资源排队拖慢**，不是被瞬时冲击打崩——典型的「持续过载」形态，靠扩容或削峰解决。

## 五、A/B 尝试：失败，但暴露了一个大坑

按方法论 §6 第 4 步做了两组 A/B（同规模 1500 并发，只改一个参数）：

| 配置 | enter p95 | 整体吞吐 |
| --- | ---: | ---: |
| 基线（默认） | 2830 ms | 526 req/s |
| 连接池 8 → 100 | 5841 ms | 289 req/s |
| Tomcat 200 → 800 | 9283 ms | 202 req/s |

看起来是「调大反而有害」。**但这个结论是错的**——我又跑了一次默认配置做回归，结果是 11545 ms，
比两个"优化"版本都慢。

**真正的原因**：每档压测都要造数，造出来的账号/智能体/答卷**一直留在库里**。
跑到第 10 轮时 account 表已经从 15 行涨到 1 万行，库越大越慢，
而"跑得越晚越慢"被误读成了"配置越改越差"。

**修正办法**：写了 `cleanup.mjs`，**每档压测前清空造数数据**，保证各档面对的库大小一致
（每档开始时都是 9 个账号 / 6 个智能体）。§四 的所有数字都是清理后重跑的。

**教训**：造数不只是"污染考生"（方法论已提醒要每场新的），
**造数本身还在撑大数据库**，会把 A/B 彻底做废。这是本轮最大的一个坑。

> 因此，**瓶颈未最终定位**。要重做 A/B，必须在清理后的干净库上，用同一批数据量对比。

## 六、容量换算

按方法论 §5.3 的经验值 `承载用户数 ≈ 并发数 × 3`（考生大部分时间在答题，不在发请求）：

| 并发 | 约当考生数 | enter p95 | 体验 |
| ---: | ---: | ---: | --- |
| 800 | **约 2400 人** | 1.06 s | 良好，建议按这个规模规划 |
| 1500 | 约 4500 人 | 2.07 s | 可用，但开考/交卷时明显卡顿 |
| 2500 | 约 7500 人 | 3.80 s | 不推荐，考生会以为系统卡死 |

> 注意：本系统的登录阶段是**错峰**完成的（客户端每批 50 人串行），
> 2500 人登录耗时约 57 秒。真实场景下考生是陆续进入的，这通常不是问题；
> 但如果要求"全员同一秒登录"，登录本身就是第一个尖峰，需要单独评估。

## 七、建议

按优先级：

1. **开考/交卷削峰**（最高性价比）
   本系统不会崩，只是慢。把「全员同一瞬间」改成「按批次间隔放行」，
   峰值并发直接降到 1/3～1/5，p95 立刻回到 1 秒内。这比扩容便宜得多。

2. **确认生产配置的连接池与线程数**
   `exam-local` 没配 Druid，用的是默认 8 条连接——这在 800+ 并发时几乎肯定是瓶颈。
   生产部署前请显式配置并压测验证（记得在干净库上做 A/B）。

3. **把 `exam-local` 的两个配置缺口补上**
   实测发现该 profile 缺 `spring.datasource.driver-class-name` 和 `jwt.secret`，
   前者导致 runtime 起不来，后者导致登录 500。压测是靠命令行参数绕过的。

4. **补测 S4 / S5**
   到点自动交卷是定时任务路径，并发行为与手动交卷不同，未覆盖。

## 八、本系统特有的坑（换项目时要改的地方）

| 坑 | 症状 | 解法 |
| --- | --- | --- |
| **交卷要求 agentId 属于考生自己的租户** | submit 全量 500「所选智能体不存在或不属于当前账号」 | 造数时必须给**每个考生租户**复制一个智能体 |
| **id 是 18 位 bigint，超过 JS 的 2^53** | 用 `Number()` 中转后 agentId 精度丢失，交卷必然失败 | 请求体用字符串模板直接写字面量，不要过 `JSON.stringify` |
| **建场次字段是 `startAt` + `durationMinutes`** | 传 `submissionStart/End` 会报「请填写考试开考时间」 | 见 `setup-exam.mjs` |
| **造数撑大数据库** | A/B 做出反向结论（见 §五） | 每档前 `node cleanup.mjs --force` |
| **考生昵称限 10 字符** | 建号失败 | 昵称用短用户名 |
| 沙箱端口重定向 | 配置端口不生效 | 启动必须显式 `--server.port` |

| 文件 | 用途 |
| --- | --- |
| `setup-exam.mjs` | 造数：场次 / 题目 / N 个考生 / 每人一个智能体。`NO_OPEN=1` 保持草稿 |

复现命令：

```bash
cd scripts/loadtest
node cleanup.mjs --force
NO_OPEN=1 node setup-exam.mjs --users=800
node exam-lt.mjs --users=800 --tag=800 --drafts=2 --think=600
python3 analyze.py artifacts/run-800.jtl
```
